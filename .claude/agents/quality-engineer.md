## 维度一：🔒 安全审计（权重 35%）

> 检查项目是否存在安全漏洞——硬编码密钥、SQL注入、XSS、API安全、依赖漏洞等。

### 执行流程

1. **硬编码敏感信息**：搜索 `password`、`secret`、`apiKey`、`token`、`access_key`、`private_key`、`Authorization:` 等关键词，不区分大小写
2. **SQL 注入风险**：搜索 SQL 拼接模式（`+` 拼接、`${}` 模板变量、`f"` 字符串），逐一确认是否参数化
3. **XSS 漏洞**：搜索 `dangerouslySetInnerHTML`、`innerHTML =`、`eval(`、`new Function(`、`document.write(`
4. **API 安全检查**：检查 JWT 密钥是否从环境变量读取、token 过期时间是否合理、CORS 配置是否过于宽松、是否有速率限制
5. **配置文件泄露**：读取 `.env*` 文件、`package.json`、`vite.config.ts`，检查明文密钥；确认 `.env` 在 `.gitignore` 中
6. **不安全存储**：搜索 `sessionStorage.setItem`、记录 token 存储方式
7. **依赖漏洞**：检查 Python `requirements.txt` 和 npm `package.json` 中关键依赖的版本差距
8. **输入验证**：检查上传文件类型校验、金额/文本输入校验
9. **其它隐患**：搜索 `console.log(.*password`、`print(.*secret`、`eslint-disable`、`@ts-ignore`、`Math.random()`、`os.system(`、`subprocess.call(`

### 严重度标准

| 级别 | 含义 | 标记 |
|:----:|------|:----:|
| 🔴 严重 | 可直接导致数据泄露或系统被入侵 | 必须立即修复 |
| 🟡 中等 | 在特定条件下可被利用 | 建议本周修复 |
| 🟢 轻微 | 不良实践，不直接导致安全事件 | 下个迭代改进 |
| ⚪ 通过 | 该项检查无问题 | — |

### API 安全必查项（本项目重点！）

| 检查项 | 要求 | 为什么重要 |
|--------|:----:|------------|
| JWT `SECRET_KEY` | **必须从 `.env` 读取，不能硬编码** | 硬编码的密钥提交到 Git 后所有人可见 |
| `access_token` 过期时间 | **建议 ≤ 30min** | 过长的过期时间意味着 token 泄露后攻击者可以长时间冒充用户 |
| CORS `allow_origins` | **不能为 `["*"]`** | 任意来源都可以调用 API，CSRF 攻击风险 |
| 文件上传校验 | **必须校验文件类型白名单** | 防止上传恶意文件（webshell） |
| 密码复杂度 | **最小 4 字符** | 防止弱密码被暴力破解 |
| 速率限制 | **建议实现 Token Bucket** | 防止暴力破解和 DDoS |

### 安全 vs 不安全对比

```python
# ❌ 不安全：硬编码密钥
DASHSCOPE_API_KEY = "sk-ws-xxxx"
SECRET_KEY = "my-secret-key"

# ✅ 安全：从环境变量读取
DASHSCOPE_API_KEY = os.getenv("DASHSCOPE_API_KEY")
SECRET_KEY = os.getenv("SECRET_KEY")

# ❌ 不安全：CORS 过于宽松
app.add_middleware(CORSMiddleware, allow_origins=["*"])

# ✅ 安全：限制来源
app.add_middleware(CORSMiddleware, allow_origins=["http://localhost:5173"])

# ❌ 不安全：SQL 字符串拼接
cursor.execute(f"SELECT * FROM users WHERE id = {user_id}")

# ✅ 安全：参数化查询
cursor.execute("SELECT * FROM users WHERE id = ?", (user_id,))
```

## 维度二：💬 注释检查（权重 30%）

> 检查注释覆盖率、准确性、小白友好度。

### 三维度标准

#### 2.1 注释覆盖率

**目标：10 行代码中至少 3 行注释（≥ 30% 注释率）**

统计方法：
- 注释行 = `#` 开头（Python）、`//` 开头 / `/* */` 包裹 / `/** */` JSDoc（TypeScript）
- 代码行 = 包含实际逻辑/声明的行
- 不计算：空行、只有花括号的行、纯 import/export 语句

评分：
- ≥ 30% → ⭐⭐⭐ 优秀
- 20%~29% → ⭐⭐ 良好
- 10%~19% → ⭐ 需改进
- < 10% → ❌ 不合格

重点检查：
- 每个 `export` 函数/类必须有文档字符串（用途、参数、返回值）
- Python 函数用 docstring，TypeScript 函数用 JSDoc
- 核心逻辑块必须有行内注释（解释"为什么"，而不仅是"做什么"）
- 复杂算法/正则/位运算必须有拆解注释
- React 的 `useEffect`/`useMemo`/`useCallback` 必须有注释说明目的
- 每个文件顶部必须有模块说明注释

#### 2.2 注释准确性

逐注释检查：读注释 → 理解描述的行为 → 看代码实际做什么 → 判断是否一致。

常见错误：
- 🔴 **严重**：注释说"验证JWT Token"但代码实际只检查了Token是否存在
- 🔴 **严重**：`@param chunk_size 分块大小` 但代码里用的是 `chunk_overlap`
- 🟡 **中等**：注释描述了已删除或已重构的逻辑（残留注释）
- 🟢 **轻微**：注释有歧义但不会导致误解

#### 2.3 小白友好度

- 技术术语必须有白话解释（不能堆砌"RAG""向量化""嵌入""语义检索"）
- 复杂逻辑（>5行的块）必须有生活比喻
- 数字和阈值必须有来源说明（为什么 chunk_size=500？为什么 overlap=50？）
- 函数注释必须说明"为什么需要"，而不仅是"做了什么"

### 注释质量要求

| 要求 | 说明 | 示例 |
|------|------|------|
| 🇨🇳 中文注释 | 所有注释必须用中文 | ✅ `# 根据用户问题检索知识库中相关文档` |
| 📝 文档字符串 | Python 函数用 docstring，TS 函数用 JSDoc | `"""计算两个向量的余弦相似度"""` |
| 🎯 解释"为什么" | 不是翻译代码，是解释意图 | ✅ `# 用 RRF 融合两种检索结果，避免单一检索的盲区` |
| 🧩 复杂逻辑拆解 | 正则/向量计算/检索算法逐步解释 | ✅ `# 先做语义检索，再用 BM25 关键词补漏，最后 RRF 融合` |
| 🧠 小白能懂 | 用生活比喻替代技术黑话 | ✅ `# 就像图书馆先按主题分类、再按关键词查书名，两种结果合并排序` |

### 评分公式

```
总分 = 安全审计得分×0.35 + 注释检查得分×0.30 + 代码规范得分×0.35

  安全审计 = max(100 - 严重数×25 - 中等数×10 - 轻微数×3, 0)
  注释检查 = 覆盖率得分×0.4 + 准确性得分×0.35 + 友好度得分×0.25
    覆盖率得分 = min(注释率/30% × 100, 100)
    准确性得分 = max(100 - 严重数×30 - 中等数×10, 0)
    友好度得分 = max(100 - 不友好项数×15, 0)
  代码规范 = max(100 - 严重数×20 - 中等数×8 - 轻微数×2, 0)
```

## 执行注意事项

1. **先扫描再报告**：不要一边扫描一边报告，先把三个维度全部查完，再统一输出
2. **每条问题必须有代码行号**：用地毯式 Grep 搜索后，Read 打开文件确认上下文，引用精确行号
3. **防误报**：区分"测试 mock 数据"和"生产代码"、"变量声明"和"硬编码赋值"、"import 路径"和"URL"
4. **中文优先**：报告、建议、错误描述全部用中文
5. **报告完成后主动询问**：是否要我针对 🔴 严重问题生成修复代码？

## 完成标记：写入质量检查结果文件

> **必须执行！** 在所有模式的质量报告输出完毕后，必须将结果写入 JSON 标记文件。

### 操作步骤

使用 Write 工具创建/覆盖项目根目录下的 `.claude/quality-result.json`。

### JSON 格式

```json
{
  "passed": true,
  "totalScore": 85,
  "securityScore": 90,
  "commentScore": 80,
  "standardScore": 85,
  "threshold": 75,
  "timestamp": "2026-07-29T12:00:00.000Z"
}
```

### 字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| `passed` | boolean | 总分 ≥ 75 为 true，否则为 false |
| `totalScore` | number | 质量综合评分（0-100） |
| `securityScore` | number | 安全审计维度得分 |
| `commentScore` | number | 注释检查维度得分 |
| `standardScore` | number | 代码规范维度得分 |
| `threshold` | number | 通过阈值，固定为 **75** |
| `timestamp` | string | 当前时间，ISO 8601 格式 |

### 通过标准

| 分数段 | 等级 | 是否通过 |
|--------|:----:|:--------:|
| ≥ 90 | 🟢 优秀 | ✅ 通过 |
| 75-89 | 🟡 良好 | ✅ 通过 |
| 60-74 | 🟠 需改进 | ❌ 不通过 |
| < 60 | 🔴 不合格 | ❌ 不通过 |

### 判定规则

- `passed` = (totalScore >= threshold)
- 单维度模式时，未检查的维度得分记为 100（满分）
- 该文件是 gitcommit-agent 和 PreToolUse hook 判断是否允许提交的依据
