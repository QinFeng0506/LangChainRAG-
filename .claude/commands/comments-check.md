对项目源码进行三维度注释质量检查——覆盖率、准确性、友好度，并给出改进建议和最终评分。

## 意图识别

收到 `/comments-check` 后，先解析用户输入，判断检查范围：

| 用户说法示例 | 检查范围 |
|-------------|----------|
| `/comments-check`（无参数） | **全部源码** — 扫描 `backend/` 和 `frontend/src/` |
| `/comments-check backend/app/rag/graph.py` | **单文件** — 只检查指定文件 |
| `/comments-check chat` | **按名称搜索** — 检查文件名包含该关键词的文件 |
| `/comments-check backend/app/rag/` | **按目录** — 检查指定目录下所有源码文件 |

---

## 检查流程

### 第一步：确定扫描范围

扫描规则：
- Python 源码：`backend/app/**/*.py`，排除 `backend/tests/`
- TypeScript 源码：`frontend/src/**/*.ts` 和 `frontend/src/**/*.tsx`，排除 `__tests__/`
- 排除：`*.d.ts`、纯类型定义文件、`__pycache__/`

### 第二步：逐文件分析

对每个文件执行「三维度检查」：

#### 维度一：注释覆盖率（权重 40%）

**目标：10 行代码中至少 3 行注释（≥ 30%）**

- Python 注释：`#` 开头、`"""` 或 `'''` 包裹的 docstring
- TypeScript 注释：`//` 开头、`/* */` 包裹、`/** */` JSDoc
- 不计入：空行、只有 `{`/`}` 的行、纯 import/from 语句

评分：
- ≥ 30% → ⭐⭐⭐ 优秀
- 20%~29% → ⭐⭐ 良好
- 10%~19% → ⭐ 需改进
- < 10% → ❌ 不合格

重点检查：
- 每个 `export` 函数/类必须有文档注释
- Python 函数用 docstring，TypeScript 函数用 JSDoc
- 核心逻辑块必须有行内注释（解释"为什么"）
- React 的 `useEffect`/`useMemo`/`useCallback` 必须有注释

#### 维度二：注释内容准确性（权重 35%）

逐注释比对：读注释 → 理解描述的行为 → 看代码实际做什么 → 判断是否一致。

常见错误：
- 🔴 **严重**：注释描述与实际代码完全矛盾
- 🟡 **中等**：注释有歧义或不完整
- 🟢 **轻微**：注释可以更精准但不会引起误解

#### 维度三：友好度（权重 25%）

- 技术术语必须有白话解释
- 复杂逻辑（>5行）必须有生活比喻
- 数字和阈值必须有来源说明
- 函数注释必须说明"为什么需要"

### 汇总评分公式

```
总分 = 覆盖率得分 × 40% + 准确性得分 × 35% + 友好度得分 × 25%

覆盖率得分 = MIN(注释率 / 30% × 100, 100)
准确性得分 = 100 - 严重问题数×20 - 中等问题数×10 - 轻微问题数×3
友好度得分 = 100 - 不友好项数×10
```

2. 🟡 **尽快补充**：缺少文档字符串的核心函数
3. 🟢 **逐步优化**：把技术术语翻译成白话
